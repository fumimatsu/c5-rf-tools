# C5による4波比較測定 → AI活用

2026-11-14合意。**次の実装はPyramid上の4波比較測定モード**とする。
本書は実装仕様・引き継ぎであり、このモードはまだ未実装。既存のRH記録/再生とは別の機能。

## 目的と今回の前提

E2=5685、E1=5705、F3=5780、F5=5820MHzを、実際に同時送信した条件で比較する。
国内利用と20MHz間隔の可否はユーザー確認済みの前提として扱う。
今回の目的は、この組み合わせの法適合や周波数間隔を再検討することではなく、
**単独時と同時送信時の測定値から、帯域内への回り込み・追加変化・変動を確認できるようにすること**。
この前提を、他の機器や利用者への一律の送信可否保証には一般化しない。

Pyramid側から先に実装する。Tab5側への移植は後の別作業。
使用chは一般プリセットから選択可能な既存設定を維持し、実験開始時の4chをセッションに固定する。
IMD候補の計算・チャンネルランキングだけで「よい環境」と判定することを、この作業の完了条件にしない。

## まず実装する範囲

1. 人によるVTX ON/OFFの確認付きで、各状態を順番に記録するウィザード。
2. 選択4chの直接測定と、同じ条件の広域走査を取得・保存する。
3. 単独/他3台/全4台と予測値を重ね、差分・変動・測定の有効性を表示する。
4. 保存した原データと設定から、実機なしでも同じ比較レポートを再生成する。

初版はCPUの計算で進める。C5ファームの変更、AI/NPU導入、自動しきい値適用、
MADSYSTEM送信、VTXの遠隔操作を同時に実装しない。
ゲート通過/非通過教示とEnter/Exit評価は継続する将来課題だが、次の一段階からは外す。

## 測定手順：4chで10状態

| 状態 | 回数 | 意味 |
|---|---:|---|
| 全4台OFF | 1 | 今回の実験の背景 |
| 対象1台のみON | 4 | 各VTX単独の周波数形状・変動、他chへの写り込み |
| 対象1台OFF・他3台ON | 4 | 対象chに他3台から入り込む帯域内電力 |
| 全4台ON | 1 | 同時送信で増減した成分・不安定さ |

各状態のON/OFFは操作者が確認する。C5の受信上昇だけで「対象VTXのONを確認済み」としない。
UIに期待するON一覧とOFF一覧を表示し、切り替え・整定後の明示操作で記録を始める。
取得前に使用できるVTX/chを確認する。4台が揃わない場合も実装・テストは進められるが、
実測の未取得状態を埋めず、4波比較の完了判定は保留にする。

最初の比較ではVTX/C5/アンテナの位置・向き、設定出力、受信設定を固定する。
ウォームアップと整定時間、測定窓、必要な有効取得数を設定・保存する。
暫定取得目安は各状態「4ch直接測定5秒＋同一条件の完了掃引3回以上」。
この時間は性能保証や品質判定のしきい値ではなく、実測で延長・再取得できる取得初期値とする。
直接測定と走査は順番に行い、同時・連続観測と表示しない。

全OFFの実験背景は既存のbackground.jsonやTab5の背景を自動上書きしない。
終了時の背景再測定を追加できるようにし、外来電波や温度などの変化が大きい場合は比較を要確認とする。
疑わしい関係を絞った後に、必要な2台の組み合わせ試験やON/OFF再確認を追加する。
固定比較の次に、コースの弱い位置・向き・実飛行で再確認する。固定位置の正常レベルを飛行中の品質基準にしない。

## 取得・保存の契約

- 使用するのはscannerの電力データ。**RH 1..254のスナップショットをRF電力比較へ流用しない**。
- 現在の`apps/pyramid/protocol.py`は`raw`と`db`（平滑値）を分けて返すが、
  既存serverの通常監視/掃引の集計は`db`を使う。新しい比較計算では有効な`raw`を線形化して集計する。
  既存の表示・保存値を生電力と見なして計算しない。既存RHアーカイブも比較用原本の代わりにしない。
- 実験全状態で、同じ測定点・順序・バッチ構成・LO/offset・gain・bw・noden・dwell/整定を使用する。
  4ch直接取得と広域掃引は取得方法を区別し、異なるLO/窓条件の値を同じ比較式に混ぜない。
- 4chの中心周波数を直接取得する。2/4MHz掃引のグリッドに中心がない場合、
  最近傍や補間値を中心周波数の実測値として表示しない。
- 原記録に受信値raw/平滑値、実取得周波数、C5時刻、ホスト受信時刻、gain、clips、flags、
  CRC/欠落、実測定窓、状態ID、実験ID、設定版、デバイス/ファーム識別を保持する。
  周波数ごとの取得時刻と走査開始/終了を保持し、WFの1行を同時測定のように扱わない。
- C5の時計のラップ・再起動や、再接続による区切りを検出する。
  無効値・欠測を0や背景値で埋めず、データ量・有効率・ばらつきと一緒に示す。
- 操作者確認のON/OFF、機体/ch対応、アナログ/デジタルなどの方式、設定出力、
  設置・アンテナ条件、確認方法を保存する。不明項目は不明のままにする。
- 原記録は保持し、再取得は別の試行として残す。途中中断・不足・再試行の状態を明示する。
  再起動・再接続後に、保存済みON/OFF確認を現在の状態として自動再採用しない。
- 新しい比較用スキーマ/保存先は版を明示し、既存config/background/RH履歴を保持する。
  実験データ・個体設定・映像はGitに入れず、実機StateDirectoryまたは無視対象の.localに置く。

## 比較計算

同じ周波数・同じ受信設定で、有効raw値`x`（receiver dB）を
`p = 10^(x/10)`へ戻し、線形電力の平均とばらつきを求める。校正済みdBmへ変換しない。

`P0(f)`を全OFF、`Pi(f)`をi番単独（背景を含む）、`P4(f)`を全4台ONの測定平均とすると、
独立な信号の電力が線形に加算され、背景・伝搬・受信特性が変化しないと仮定した予測は：

```text
P_expected(f) = P0(f) + Σi=1..4 [Pi(f) - P0(f)]
              = Σi=1..4 Pi(f) - 3 P0(f)

残差 ΔP(f) = P4(f) - P_expected(f)
参考の予測比 ΔL(f) = 10 log10[P4(f) / P_expected(f)]
```

`ΔL`は分子・分母が正で、比較条件と取得が有効なときだけ表示する。
背景差引きの負値や小さすぎる推定値を0へ丸めて、品質評価に使わない。
負の残差も保持する。追加電力だけでなく、受信圧縮・条件変化などによる減少も要確認の材料となる。
残差には測定ばらつき・経時変化も含まれるため、IMD量と断定しない。
各周波数の取得数・ばらつき・繰り返し再現性を併記し、普遍的な±何dBの合否を仮定しない。

各対象chでは、他3台ON/対象OFF時の実測を背景・対象単独と並べる。
この帯域内電力はC5の受信窓での観測であり、映像受信機の真のC/I・SNRや復調品質ではない。
4台ONの合計電力が上がっただけで、対象信号が強くなった/環境が改善したと評価しない。

## 画面

大画面を主対象に、直角・白灰基調とch別識別色を維持する。

- 上：現在の測定状態、ON/OFF確認、整定/取得進捗、中断/再取得、比較条件の一致。
- 中央：背景・4つの単独・予測合成・全4台実測を切り替え/重ね合わせ。
  別グラフに符号付き残差、別の記号でIMD計算候補。取得点・時間分解能を明示。
- ch別：対象単独、他3台のみ、全4台、変動、データ量/欠測、根拠付き注意。
- 右：実験状態の一覧、試行/記録の選択、条件、測定の有効性。

表示例は「E1：対象OFF・他3台ONで帯域内上昇」「4台ONで予測との差を観測」「比較条件不一致」。
「IMD発生確定」「VTX不良」「映像良好」をC5のみから表示しない。
初版は数値と根拠を優先し、色を付ける場合も取得不足は灰色、測定上の注意と映像品質を区別する。
判定ルールと版を残し、未検証の固定しきい値を合否保証として隠し込まない。

## 完了条件と明日の作業順

1. 現在のcheckout/実機版・接続先・所有C5・記録状態を確認。接続はdocs/development.mdに従う。
2. 比較計算と保存形式を実装し、既知の線形加算、追加成分、負の残差、背景ノイズ、
   欠測/クリップ、非正の分母、周波数/設定不一致、中断・再取得のテストを通す。
   合成テストデータはテスト用と明示し、本番のRF値として表示しない。
3. 操作者確認付き10状態の記録、読出し、比較画面を実装し、保存後も同じ結果が再生成できることを確認。
4. PCのPythonテストとJS構文、実ブラウザーで大画面・操作・欠測表示を確認。
5. 実機へは旧版/既存状態を保持して配備し、利用可能なVTXで確認する。
   全OFF・各状態の切替はユーザーへ依頼し、4台が揃った時点で10状態の比較を検証する。
6. 生データの取得/条件照合、画面、保存/再生、実RF、映像での裏付けを別々に報告する。
   C5だけの比較が完成しても映像品質や物理ゲート精度まで検証済みとしない。

稼働中のRH記録は勝手に中断せず、比較測定との排他を実装する。
この段階でTab5/C5ファームやNPUメモリ配分、既存の別サービスを変更する必要はない。

## 次段階：比較記録を使ったAI/NPU

1. まずCPUの比較・単純な変動検出を基準にする。小型モデルで、複数帯域同時上昇・
   反復する落ち込み・帯域形状の変化などを分類する候補を評価する。
   波形のスクリーンショットだけではなく、測定配列・時刻・有効マスク・条件を入力候補にする。
2. 操作者のON/OFF確認は測定状態のラベルであり、「干渉」「故障」の正解ラベルではない。
   通常の機体移動・設置変化、測定器側の歪みを含め、人の確認と別測定で根拠を残す。
   不明/未学習を出せるようにし、学習と評価は別の試行/日/機材で行う。
3. CPUの単純判定より効果があることを確認したモデルを、PCで学習しPyramid NPUへ変換・配備する。
   変換/量子化後の精度・処理時間・受信/保存への影響を実機で確認する。現時点でモデル実行は未検証。
4. その後、映像受信機の映像を時刻付きで取り込み、方式別の乱れ検出とRF変化を照合する。
   HDMI入力1系統だけで4ch映像を同時観測できるとは扱わず、入力構成と同期誤差を別に検証する。

AIは未観測区間を観測済みにせず、推測によって元の測定値を埋めない。
AIの注意と計測しきい値制御は分ける。自動Enter/ExitやMADSYSTEM連携は、さらに別の検証段階とする。
