## 開始時

1. root/対象アプリのAGENTS.md、docs/development.md、[4波比較測定の仕様](four-wave-comparison.md)を読む。
2. Gitのbranch/HEAD/差分を確認。Pyramidの実行版とcheckoutの版を別々に確認。
3. 接続先はユーザーのローカル設定。C5は各アプリ専用の別個体で、Tab5側・Pyramid側を入れ替えない。
4. まずPCテスト/ビルド。SSH認証・書き込み先が不明なら推測して書かない。

## 次の一段階：C5で4波を比較する

最初の対象はE2=5685 / E1=5705 / F3=5780 / F5=5820MHz。
国内利用と20MHz間隔はユーザー確認済みの前提で、実際の4波同時運用時の変化を確認したい。

1. 全機OFFの背景、各1台のみON（4回）、対象1台OFF・他3台ON（4回）、全4台ONを記録する。
2. 各状態のON/OFFは人が確認。初期比較は位置・向き・設定を固定し、その後に弱い位置や実飛行で再確認する。
3. scannerの有効rawを線形電力として集計し、単独の足し合わせ予測と全4台の実測を比較する。
   現行serverの通常表示は平滑値を使うため、そのまま計算原本にしない。RH値も流用しない。
4. 対象chに他3台から入り込む電力、同時送信による追加変化、時間変動、測定の有効性を表示する。
5. 原記録・状態確認・条件を保存し、オフラインで同じ比較を再生成できるようにする。

取得窓・保存項目・計算式・UI・完了条件は[実装仕様](four-wave-comparison.md)を正とする。
4台のVTXが揃うかは実機試験前に確認し、不足してもソフト実装は進め、未取得データを実測として埋めない。
既存の背景・設定・RH記録を保持し、記録中のセッションを勝手に止めない。

## その後：AI/NPU

比較記録と人の確認を蓄積し、CPUの単純判定を基準に、小型モデルの変化パターン判定を評価する。
効果を確認したモデルをNPUへ移し、精度・速度・受信/保存への影響を検証する。
さらに映像受信機の映像乱れとRF変化を時刻照合する段階へ進む。
ON/OFF確認は測定状態のラベルであり、干渉や故障の真値ではない。C5だけで映像良好を保証しない。
ゲート通過教示の保存機能は0.2.2で追加済み。今回のR8 ON/OFFは通過ラベルではない。物理通過と非通過の対照試験はユーザー希望で次回。自動Enter/Exit、MADSYSTEM送信は後続の別段階として扱う。

大画面で情報密度を高め、角丸・装飾を抑え、ch色・測定状態・欠測を区別して随時ブラッシュアップする。
