# Pyramid Proの4ch LEDメーターと背景取得ボタン

Pyramid Proの側面LEDは受信メーターに使えます。Pyramid 0.2.5では上部ボタンから背景を取得し、上部LEDで進捗を確認できます。

## 実機と公式資料で確認したこと

- Pyramid ProはRGB LEDを48個搭載。対象実機で `ec_proxy.service` が稼働し、`ec_cli device --rgb_size` は48、`ec_cli device --rgb` はモード1、`ec_cli device --version` は1を返した。
- 実機のCLIは `rgb_set_color` / `rgb_get_color` と `ec_cli echo --button` を公開している。公式の個別LED制御はモード0。1コマンドは1個を指定するため、更新レートは実測で決める。
- 上部ボタンの短押しには工場出荷時の音声アシスタント操作があり、長時間の長押しには強制電源OFFがある。0.2.4稼働中の実機で短押しと長めの押下を観測した。Linux入力とEC通知の両方で、KEY204は押下時に0、解放時に1。EC通知でキー番号のフィールド名は `vale` だった。
- ベンダーのSTM32ファームは、0〜11番を上部、12〜47番を4本×9個に割り当てている。実機でモード0への切り替えと単灯の発光を確認し、0〜11番は上部で点灯した。

参照：[Pyramid Proの仕様](https://docs.m5stack.com/en/ai_hardware/AI_Pyramid-Pro)、[EC Proxy制御](https://docs.m5stack.com/en/compute/ai_pyramid/ec_proxy)、[上部ボタンの工場出荷時動作](https://docs.m5stack.com/en/compute/ai_pyramid/getting_started)、[EC Proxyソース](https://github.com/m5stack/AI-Pyramid-EC-Proxy)、[STM32 RGB実装](https://github.com/m5stack/M5AI-Pyramid-Internal-FW/blob/a8f7a9ffc4267b33d489fc0ee8dbd63d73bfda27/code/M5_650N_Pyramind_STM32/Drivers/M5_Pyrmind_Drivers/Src/rgb.c)。

## 側面LEDメーター

物理バー1本をWebの1枠へ対応させ、本体LEDは枠順に赤・緑・青・黄を使う。初期の対応はE2・E1・F3・F5で、Webで選び直したら枠のチャンネルに追従する。端から連続して光らせ、受信が強いほど点灯数を増やす。

OLED側を正面として、以下の順にインデックスが下から上へ進みます。

| Web枠 | 初期ch | 位置 | 本体LED色 | LED番号（下→上） |
|---|---|---|---|---|
| 1 | E2 | 正面左 | 赤 | 30–38 |
| 2 | E1 | 正面右 | 緑 | 12–20 |
| 3 | F3 | 左奥 | 青 | 39–47 |
| 4 | F5 | 右奥 | 黄 | 21–29 |

点灯数の入力は `Monitor.monitor_loop()` が100msごとに集計する `levels` の receiver dB。4ch監視の `live`・`fresh` 条件に限定し、欠測した枠は消灯する。帯域走査とRH計測ではECの元の点灯モードへ戻す。0.2.5では背景取得中に側面を消灯し、上部に進捗を表示する。全枠共通の初期範囲は−6〜+21 receiver dBで3 dBごとに1段。点灯数は0〜9の範囲に収める。

`c5-led-meter.service` がループバックの `/api/state` を読み、低輝度で変化したLEDだけ更新する。制御間隔は0.25秒以上、1回の更新は最大12個。0.2.5の制御範囲は側面12〜47番と本体上部。上部0〜10番で状態を表示し、11番は消灯する。ECへのアクセスは標準CLIを通し、C5の受信と別サービスで動作する。実機のECソケットはroot所有で他ユーザーへの書き込み権限がないため、LED側だけをrootで実行し、ファイル書き込み・デバイス・接続先を制限した。受信側は従来のDynamicUserで動く。

`/etc/c5-led-meter.env` の `C5_LED_BARS` に、Web枠順で4本のインデックス配列を指定する。各配列は伸びる順に9個。物理的な対応を確認してから有効化する。`C5_LED_LOW` と `C5_LED_HIGH` で全枠共通の範囲を調整できる。停止は `systemctl disable --now c5-led-meter.service`。停止時は取得前のRGBモードへ戻す。既に手動モードが使われているか、動作中に他プロセスが別のモードへ移した場合は、その監視セッションの点灯制御を譲る。同じ手動モード内で別プロセスが色を書き換えるケースは未検証。

```ini
C5_LED_BARS=[[30,31,32,33,34,35,36,37,38],[12,13,14,15,16,17,18,19,20],[39,40,41,42,43,44,45,46,47],[21,22,23,24,25,26,27,28,29]]
```

## 0.2.5の上部ボタンとLED

1. 4ch監視がLIVEで上部に緑が1個点いているとき、上部ボタンを約1秒押して離す。上部11個が黄になる。
2. **ご自身のVTXをすべてOFF**にしたことを確認する。最初に離してから12秒以内にもう一度約1秒押して離す。この操作で背景取得を開始する。確認が間に合わなければ黄が消え、通常表示へ戻る。
3. 詳細走査5回の進捗を上部の青の長さで表示する。保存すると緑11個、失敗すると赤11個が約3秒点灯する。完了後は4ch監視へ戻る。

各押下は0.7〜2.5秒間で、押したままでは開始しない。記録とその終了処理中、4ch監視以外、受信が止まっている間は物理操作を受け付けない。確認中にプロファイルや受信セッションが変わった場合も取り消す。上部表示には0〜10番を使用する。

`ec_cli echo --button` のKEY204の押下・解放を購読する。EC設定と工場出荷時の入力経路には書き込まず、既存のOrigin／トークン検査付きの制御APIを経由する。ボタン用の取得IDでWebからの取得と区別する。既存の背景保存を使い、欠測時は前の背景ファイルを保持する。

背景は帯域走査とウォーターフォールで使う。側面LEDは4ch監視の受信値に連動する。ラップ計測のしきい値は別スケールのRH値で設定する。

## 実機検証

### 0.2.4：側面LED
- 4ch監視でF3のVTXだけをON/OFF。静置条件でF3はOFF約−4、ON約+27〜+30 receiver dB。左奥のバーが1→9→1個になることを、目視とECの色レジスタで確認した。ON保持中、他3本の読み戻しは各1個。最終配色は赤・緑・青・黄をECから照合した。
- 約3秒ずつの観測で、LED導入前は約1,921フレーム/秒、F3をONにして点灯中は約1,912フレーム/秒。両方でCRC・欠番・C5 drops・RFエラーの増加は0。E2/E1/F5の個別VTX試験、長時間負荷、電源再投入、音声機能との同時動作は未確認。
- Python試験25件はPCとPyramid上で成功し、JavaScript構文検査にも成功。LEDサービスの停止時に元のRGBモード1へ戻った。

### 0.2.5：背景ボタン

LAN経由でWebのHTTP 200と4ch監視のLIVEを確認した。更新前後で既存データのSHA-256が一致し、PCとPyramidでPython試験32件が成功した。

全VTX OFFで物理ボタンを2回操作した。1回目の後は黄11個で、2回目まで背景取得は開始しなかった。2回目で詳細走査が始まり、青は1→2→4→7→9個。約4.8秒で背景を保存し、緑11個が約3秒点いた後、緑1個の待機表示と4ch監視のLIVEに戻った。色の遷移は目視とECの読み戻しで一致し、上部の11番は消灯のままだった。

背景ファイルは137点すべて取得し、欠測0。APIで保存完了・採用済みを確認した。保存前後で更新されたファイルは背景のみで、設定と記録のSHA-256は一致。失敗時の赤表示と本体の電源再投入は実機未確認。

## 更新と復旧

[開発手順](development.md)に従い、旧アプリと2つのユニット定義を保存してから更新します。LEDサービスを止めて受信サービスを切り替え、4ch監視がLIVEに戻ってからLEDサービスを起動します。旧版へ戻す場合も記録と終了処理の停止を確認し、同じ順で保存したユニット定義を復元してください。環境設定と `/var/lib/c5-monitor` は保持します。
