# 電波監視・計測自動化の設計方針

2026-11-13 / 検討結果。以下の自動判定・自動適用は未実装。
ユーザーの優先事項は、AI搭載そのものではなく、電波の乱れの検出と計測しきい値調整の省力化。

## 実機で確認した範囲

- AI Pyramid-Pro、Ubuntu 22.04、8 CPUコア。既存サービスを維持。
- C5受信サービスの確認時点の `ps` はCPU 37.6%（1コアを100%とする尺度）、RSS 23492KB。
  この値は確認時点までの平均で、推論との同時負荷ベンチマークではない。
- `/proc/cmdline` は `mem=2048M`、LinuxのMemTotalは約1912MiB。
  `/proc/ax_proc/mem_cmm_info` の予約領域は6144MB。
  公式Pro説明の標準4GB+4GBと異なり、この実機はOS約2GB・メディア用約6GB。
  ハードが非Proという意味ではない。まず現状のまま小さく検証する。
- `/proc/ax_proc/chip_type` は `AX650C_CHIP`、NPU procfsと `/opt/bin/ax_run_model` が存在。
  マーケティング仕様のAX8850/24TOPSと、実装で使うAX650系SDK名を混同しない。
  axcl-smiはPATHにない。PCIeホスト用AXCLサンプルをそのまま動作済みと扱わない。
- 工場出荷のllm系サービスが存在。無断停止・モデル導入・メモリ割当変更はしていない。
- 初版0.1.0は実C5受信、背景記録、4/2MHz走査、RH36設定/ポーリングとR8 ON/OFFを確認。
  初版の検証は.local/evidence/0.1.0、現行0.2.0は.local/evidence/0.2.0。
  0.2.0で時刻付きRH記録と再生を追加。物理的なゲート通過精度とMADSYSTEM送信は未検証。

## 自動化の優先順

### 1. 計測の自動セットアップ（最優先・CPUで開始）

全機OFFの背景、各機の教示通過、コース内の非通過走行を区別して記録する。
各chで「ゲート通過時の弱い側のピーク」と「非通過時の強い側の山」の分離を評価する。
進入EnterAt、退出ExitAt、退出後の結合時間、最小通過間隔を候補として評価する。
ピークだけの固定割合では、遠方の強い山・マルチパス・VTX起動を分離できない場合がある。

候補ごとに、見逃し、余計な検出、二重検出、通過終了の遅れ、通過時刻のズレを別々に示す。
しきい値で分離できない場合は「要設置調整／分離不足」と表示し、自動設定に成功した扱いにしない。
ゲートアンテナ・受信機位置・遮蔽の変更も候補となる。CPU/NPUの増強では解消しない場合がある。

初期は「学習→提案→別走行で比較→適用」。十分な検証後に自動適用の対象を増やす。
計測中も候補を計算できるが、当初の実適用は通過中を避けてレース間などで行う。
理由：現行C5のEnter/Exit書き込みは進行中のcrossingを解除する（rh_usb.cpp applyWrite）。
これは初期実装の継続性確保であり、レース中の適応を恒久的に禁止する仕様ではない。

### 2. 電波変化の自動検出（CPUで開始）

- 無送信背景に対する上昇、時間的な断続、短い落ち込み、想定帯域外の上昇。
- 通過ごとのピーク・山幅・非通過との差を比較する。機体の移動による変動を異常と決めつけない。
- 1台ずつONにしたときの、他の周波数での変化を記録し、後の複数機ONと比較する。
- 異常の時刻と同時に変わったchを示すが、相関だけで加害VTXを特定しない。
- 幅広い上昇は「観測帯域が広がった」と表現し、発振不良・スプリアス・混信と即断しない。
  C5の測定帯域、周波数応答、飽和、外来Wi-Fiや別の送信源も区別が必要。

色は観測目的ごとに分ける。例：計測の緑=分離を確認、黄=余裕低下/情報不足、赤=分離不能/欠測。
「クリーン」「VTX良品」など絶対的な品質保証にはしない。未学習・未観測は灰色。

### 3. NPUを使う候補

1. 複数chの時系列・帯域画像を使う小型CNN/時系列モデル。
   教示済みの通過、起動、持続ノイズ、断続干渉などのパターン分類を補助する。
   初めにCPUの単純な方法と比較し、別日・別場所・別VTXで改善が残るかを確認する。
2. 外部カメラ映像の機体/ゲート通過検出。
   RFの山の独立した確認材料に使う。小さく高速なドローン用のデータと時刻同期が必要。
   フレームレートや露光、遮蔽に制限があり、映像だけを無条件に正解にしない。
3. ProのHDMI入力からの映像乱れの検出とRF変化との照合。
   ブロック状破綻・映像停止・アナログノイズなどを、方式別に学習/検証する。
   1つの映像入力/受信機で4機の映像を同時に確認できるわけではない。
4. 数値で確定した事象の説明文や音声アラート。
   LLMの説明からしきい値や計測時刻を直接決めない。優先度は上記より低い。

独自モデルはONNXからPulsar2で量子化・AX650用axmodelへ変換し、実機で精度/速度を確認する。
学習はPCなどで行い、Pyramidでは推論を担う構成をまず想定する。
24TOPSは任意Python処理の高速化や、異常原因の識別精度を保証しない。

## 記録を先に整える

0.2.0ではRHのREAD_LAP_STATSの元16バイトと、極値・crossing・ピーク・カウンター・RTT・
設定・周辺のC5時刻読出し・遅延/欠測情報を保存し、読み取り専用で再生できる。
描画時刻はホスト推定であり、C5の厳密な時刻同期は未実装。RHではRF詳細フラグは提供されない。
ブラウザー表示用の100ms集約・250ms最大値だけを、細かい通過学習の原本にしない。
現行APIの極値履歴はフル1kHzサンプルの代わりではなく、完全なネイティブ検出再現も保証しない。
必要性が確認されたら、RF計算を変えずに計測中の入力列を転送するC5ファーム拡張を別版で検討する。

正解ラベルは人の確認や同期映像などで作る。同じC5から生成されたMADSYSTEM結果を、
独立した真値として学習・検証の両方に使わない。練習走行と検証走行も分ける。

計測モードでは広域走査を行わない。広域変化の連続監視を同時に必要とする場合は、
2台のC5で計測と広域監視を分ける案を比較する。NPUを追加しても1無線部の観測時間は増えない。
