# Pyramid 0.2.2：全フレーム記録・独立ラベル・学習用原データ

2026-11-14。既存Pyramidへ配備。C5MK 1.2.5+xiaoc5、Tab5、別サービス、NPUメモリ設定は変更していない。
10状態の4波比較ウィザードとAI/NPU推論は未実装。この版はそのための記録基盤を追加する。

## 操作

1. **4CH監視**でchを選び「全フレーム記録開始」。集計前のUSBペイロードを保存する。
2. **計測・記録**で「RH計測を記録開始」。従来どおりRH36のスナップショット・極値・C5判定を保存する。
3. 記録中のモード・ch・背景変更は拒否する。停止後、保存完了を待って切り替える。切替はファーム書き込みではない。
4. 右の一覧で記録を選び「選択記録を再生」。scannerはRAW/生電力とFILT/平滑値を切替可能。
5. 人の教示は対象chを1つ選び「通過」「非通過」「不明」。初期運用は1ch・1機。
   RFを見ずに教示するときは「RFを隠して教示」を使う。記録者・不確かさ・メモも保存する。
6. 再生では開始/終了秒を指定する。「再生位置を使う」は表示窓の終端を入力する。
   位置指定は `human_replay`、外部映像で人が確認した場合だけ `human_video_review` を選ぶ。
   外部映像の同期機能はない。時刻合わせの誤差も不確かさへ含める。
7. 訂正は対象の有効ラベルを選び「訂正」して分類ボタンを押す。取消は「選択ラベルを取消」。元の行は残る。
   ライブ中の訂正は元の時刻を保持する。再生中の訂正は指定した時刻・区間を保存する。
8. 停止済みscannerの「記録JSONL」はbase64ペイロード原本。「学習用JSONL」は復号済み値とラベル監査履歴。

ヘッダーに単位・記録ID・経過・欠落、右側に実機モード・空き容量・保存状態を表示する。
再生時も実機の受信は継続する。再生時のch/単位と、実機の診断を混同しない。
`SOFTWARE TEST` は操作・負荷試験で、評価の正解データには使わない。

## 保存形式

保存先は既存StateDirectory。旧アーカイブ、背景、設定は移行・削除しない。

| 対象 | 保存先 / 形式 | 意味 |
|---|---|---|
| native | `recordings/<id>.sqlite3` / `c5-native-recording/1` | RH 1..254。従来形式を維持 |
| scanner | `recordings/<id>.sqlite3` / `c5-scanner-recording/1` | receiver dB。CRC確認済みUSBペイロード |
| 人の教示 | `labels/<id>.labels.sqlite3` | 元記録とは別の追記専用台帳 |
| 学習用出力 | ダウンロードまたはCLI出力 / `c5-training-source/1` | manifest・ラベル履歴・復号値。学習済みモデルではない |

scannerのテーブル：

```sql
metadata(id INTEGER PRIMARY KEY, data TEXT)
frames(record_seq INTEGER PRIMARY KEY, t REAL, receivedUnix REAL, kind TEXT, payload BLOB)
events(seq INTEGER PRIMARY KEY, t REAL, data TEXT)
CREATE INDEX frames_time ON frames(t, record_seq)
```

`record_seq` はホスト側の保存順。C5の16bit `seq` を主キーにしない。
`t` はセッション開始からのhost monotonic秒、`receivedUnix` はホスト受信時刻。
各chのC5 µs時刻、raw/filt centi-dB、MHz、gain、clips、flagsはペイロード内に残る。
表示用 `values()` の除外を保存には適用しない。R以外や解釈不能なCRC-validフレームも種別・原バイトを残す。

metadataには実際に送るprofile/scannerコマンド、ch/MHz、版・個体、背景の時刻/採用状態、単位・時刻基準・取得表現を保存する。
`nativeCrossingAvailable=false`、`rhScale=not applicable` をscannerへ明示する。
CRC-invalidのワイヤーバイトは保存せず、CRCエラー数を別に記録する。

C5側drops、ワイヤーseq欠番、ホストキュー溢れは別々に数える。重複し得るので合算しない。
seq/µs時刻/dropsのwrapとカウンターリセットを分ける。
既知の欠落・リセット・不正ペイロードがある記録は `incomplete`。中断時は `interrupted` と表示する。
`complete` は記録経路の完了状態であり、RFの正常・通過の正解を意味しない。

## 書き込み・再生の負荷

scannerキューは16,384件。受信側は非同期enqueueだけ行い、約100ms/最大1000件で `executemany` とcommit。
DB作成も保存スレッドで行う。初期化を受信スレッドで行った候補では開始時に58件の欠番/C5 dropsが出たため修正した。
キュー溢れは `queue_overflow` で停止して保持済みデータをflushし、完全な記録として扱わない。

空き容量の既定下限は256MiB（`--disk-min-mib`）。開始前と記録中約0.5秒ごとに確認し、下回ると `disk_low` で停止する。
この記録中の低容量停止はscannerに実装した。nativeは開始時確認と従来の保存エラー停止を維持する。
古い記録の自動削除はない。低容量は停止理由として保存する。突然の電源断では直近未commit分を失い得る。

scanner再生は最大30秒/100,000フレームから500時間ビンへmin/max集計する。
raw/filt・gain/flags/clips・欠番を保持した表示で、上限に達した場合は省略を明示する。原本の間引きはない。
重いscanner集計は1つの読み取り専用プロセスへ分離し、待機要求も1件に制限する。
raw scanner/学習用のエクスポートもUSBを開かない別プロセスで行い、64KiB単位で転送する。同時エクスポートは1件。
nativeのRH軸とscannerのdB軸を混ぜない。いずれの再生もC5判定のオフライン再実行ではない。

容量をペイロードだけで見積もらない。PCの100,000件/68Bペイロード試験では、索引込みSQLiteは約119B/件、
1,000fpsで約409MiB/時だった。実機は約1,920fpsなので、初期案の250〜300MB/時を前提にしない。
WAL、イベント、ラベル、ダウンロード出力は別途容量を使う。実測のサイズ/レートは画面でも確認できる。
実機の186.4秒/358,430件は確定後42.4MiBで、同じ条件なら約0.8GiB/時（WAL等を除く）。

## ラベルとAI学習の境界

台帳のUPDATE/DELETEは禁止し、訂正・取消は `operation` と `supersedes` の新しい行で記録する。
同一ID・同一内容の再送は重複を作らない。C5 `pass` 行や `passes.jsonl` から人のラベルを自動生成しない。

ボタンは**サーバーへ到着したhost monotonic時刻**を採用する。ブラウザーの時計やボタン押下時刻そのものではない。
初期値±1秒は操作上の見積りで、遅延の実測保証ではない。
RFを見て時刻を選ぶと山の位置に引かれるため、`viewedRfWhileLabeling=true` を残す。
RF非参照は操作者申告であり、独立性をシステムが証明した意味ではない。

学習用manifestは記録の単位・品質・ラベルrevision・`splitGroup=recordingId` を持つ。
訂正前/取消済みの行も監査履歴として出力する。`independentlyReported` は有効な通過/非通過で、RF非参照申告かつ
live/video確認、software_test以外の場合だけtrue。`evaluationGroundTruthVerified` は常にfalse。
ラベルの点・区間・不確かさからフレーム全体を勝手にクラスへ変換しない。C5判定も正解へ流用しない。

```sh
cd apps/pyramid
python3 dataset.py --data /var/lib/c5-monitor --recording <ID> --out <新規出力先>.jsonl
```

出力先は新規作成のみ。原本は書き換えない。HTTP：`GET /api/recordings/<id>/training`。
raw原本：`GET /api/recordings/<id>/export`、ラベル台帳：`GET /api/recordings/<id>/labels`。
操作・ラベル追加POSTは既存のtoken/Host/Origin確認を通す。認証/TLSの代用ではなく、信頼できるLAN専用。

これで学習用の材料を保存・持ち出せるが、正解付きデータセットの完成ではない。
実際の通過/非通過、別試行・別日・配置/機材を分けた評価を先に集める。
同じ走行を隣接窓や別記録へ分けて学習/評価へ混ぜない。recording単位のグループは最小限の識別で、独立性の保証ではない。
CPUの単純な判定を基準に評価し、効果の確認後にNPU変換・量子化後の精度と受信への影響を検証する。
まだモデル学習、NPU推論、自動Enter/Exit、MADSYSTEM送信は実装していない。

## 確認済み

- Windows Python 3.12 / Pyramid Ubuntu Python 3.10：20テスト成功。JS両ファイルの構文チェック成功。
- 原ペイロード一致、flags/clips/gain異常値の保持、wrap/欠番/overflow、`disk_low` flush、ラベル追記・訂正・取消、
  イベントからの自動教示なし、記録中の切替拒否、HTTP操作保護、source DBのハッシュ不変を試験。
- 実C5・4ch fast/gain30/offset10/bw1/noden256/alpha0.3。候補版の保存単体負荷試験：
  非記録15.2秒で1921.6fps / CPU53.6%、約186.4秒記録で358,430件 / 約1923fps / CPU108.7%。
  CPUは受信サービス本体の1コア100%尺度。RSS約30.7→31.1MiB、物理書込み約680KB/s。
  再生用/出力用子プロセスの追加CPU・メモリを含む総負荷値ではない。
- この3分記録はホスト欠落0・seq欠番0・C5 drops増加0・CRC0。約3分までの結果で、30分連続試験ではない。
- 30秒/約57,700件の再生窓を4回読み出しながら17.7秒/33,974件を記録し、欠落指標はいずれも0。
  再生APIは実機loopbackで約3.2〜3.5秒/窓。画面の再生要求は重ねず、最新のシークを待機する。
- ユーザー確認によるR8 ON/OFF試験：ON時約17〜31 receiver dB、OFF時約−4。100,209件、欠落指標0。
  これはRF反応試験で、通過や良好な映像のラベルではない。背景は取り直していない。
- 実33,974フレームのbase64出力を原SQLiteと逐次照合し、全ペイロードが一致。学習用出力も全33,974件を復号。
  最終版の原本出力約3.0秒、学習用約8.4秒。この両出力と同時に22,851件を記録し、欠落指標はいずれも0。
- UIでraw/filt切替・シーク・独立ラベル訂正/取消・RF非表示を確認。旧native履歴もRH単位で再生可能。
- 既存2件のnative SQLite SHA-256は配備前と一致。ソフト試験記録とそのラベルは `software_test` として区別。

## 未確認・次の段階

ユーザー希望で、物理ゲート通過/非通過試験は次回。今のデータで通過精度や分類精度を出さない。
dB↔RH換算、USBの物理抜き差し、Pyramid全体の電源再起動・突然の電源断は今回未確認。
scanner全受信フレームはI/Qでも、C5内部1kHz波形全部でもない。RH中はscanner出力が止まる。
RF詳細診断の更新周期やC5の前処理もあるので、flags=0だけで受信の線形性を保証しない。
これだけでC5通過ロジックを同じ結果まで再現できるとは結論しない。

次の機能は[4波比較仕様](../../../docs/four-wave-comparison.md)の人による10状態確認・比較計算・広域記録。
今回のラベルはゲート通過用で、VTXのON/OFF状態や「干渉/故障」の真値とは別物。

## 配備と戻し方

現行：`c5-monitor.service` → `/opt/c5-monitor/0.2.2/server.py`。
`/etc/c5-monitor.env` へ実機で照合した `C5_SERIAL` を保持する。個体値・認証はGitへ入れない。
0.2.1は単独配備せず、その可搬設定を0.2.2へ含めた。0.2.0コード・元サービス定義・StateDirectoryは保持。

更新/rollbackの直前に `/api/state` で `recordingActive=false`、`recording.closing` もfalseであることを確認する。
記録中のユーザーセッションを中断しない。再起動後にLIVE・個体・設定・背景の保存を確認する。

```sh
# 上の停止確認後、旧0.2.0へ戻す場合のみ
cp /opt/c5-monitor/0.2.0/service-before-0.2.2.txt /etc/systemd/system/c5-monitor.service
systemctl daemon-reload
systemctl restart c5-monitor.service
```

`/var/lib/c5-monitor` を削除/置換しない。旧版はscannerアーカイブや新ラベルを利用できないが、ファイルは残す。
サービス再起動では記録OFF・背景未採用に戻る。背景の再記録は全VTX OFFの確認後のみ。
最終の設定は試験前のE2/E1/F3/F5へ戻し、R8試験のチャンネル情報はアーカイブ内に保持する。

## 元案/旧文書との相違

- 初期案の `frames.seq` 主キーは `scanner_recording.py` の `record_seq` へ変更。C5 seqのwrap/欠番とホスト順を分けるため。
- 通過ラベルはJSONL案の代わりに `labels.py` の独立SQLite台帳。訂正/取消は追記・元行保持。
- `apps/pyramid/AGENTS.md` と `docs/handoff.md` の「教示を延期」「0.2.0配備済み/0.2.1未配備」は、
  後続の実装指示と今回の0.2.2配備に合わせ更新した。4波10状態比較は依然未実装。
- `server.py` の原フレーム破棄経路を保存フックへ変更し、重い再生/出力は受信から分離。
  受信スレッド内のDB初期化と同一プロセス内の大量再生は実機で欠番を起こしたため採用しない。
- ペイロードだけの250〜300MB/時見積りは索引/WALを含まない。実測容量を基準に運用する。
