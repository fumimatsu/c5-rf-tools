# Tab5 0.5.1：通信品質と評価区間・表示の修正

2026-11-14。接続したTab5をESP32-P4と照合し、0.5.0から0.5.1へ更新した。
Pyramid、別個体のC5、C5MKファーム、SDK/BSPの起動順序は変更していない。

## 実装

- CRC不正・不正フレーム長はデコーダー内で即通知し、同じ受信塊の後続フレームを集計する前に無効化する。
  CRC-validだがRの形式が不正な場合も区別する。後続の有効フレームは引き続き解析する。
- seq欠番、C5 drops増加、重複、カウンター再同期、C5時刻逆行も評価側へ伝達する。
  16bit seqと32bit dropsの周回を扱い、リセットを巨大な欠番数・増加数として数えない。
- 4ch監視の該当100ms枠を不完全にし、正常基準のOFF/ON記録中は通信エラーで保存を拒否する。
  保存済みの背景・正常基準は消さない。判定は灰色にし、連続100枠の有効データを取り直す。
  直近1秒は「通信欠落」、以降は評価待ちを表示する。RF不調や映像品質低下の赤判定へ置換しない。
- 掃引中の不連続も現在の取得群を無効とし、不完全な点を通常の測定値にしない。
- カードの測定注意を、USB CRC / SEQ GAP / C5 DROP / FRAME ERROR / C5 RESET / DUPLICATE と、
  RF取得失敗 / 飽和・CLIP / GAIN不一致 / 代替取得 / RAW・FILT欠測へ具体化した。
  RF側の理由は最後の不正値の情報を約1秒保持する。複数理由はflagsと診断カウンターでも確認できる。
- 数値欄は `FILT dB`、背景採用時は `F-BG dB`。RAWの100ms線形電力平均・PKを使う履歴と区別する。
  元の値・計算式・正常判定しきい値を変更していない。F-BGは既存の保存背景との差で、SNRではない。
- 上部に実際のapp descriptorの版、下部に受信Rフレーム/秒と診断カウンターを表示する。
  新しい日本語に合わせ、同じ検証済みNoto Sans JP入力から279字の20/24pxフォントを生成した。

## カウンター

| 表示 | 意味 |
|---|---|
| R …/s | CRC・R形式を確認した受信フレームの約1秒間レート。周波数設定の確認待ちも含む。掃引回数/秒ではない |
| CRC | 現在のUSB接続でのCRC不正フレーム数 |
| SEQ | Tab5起動後に検出したR seqの欠番。USB接続の初回フレームは基準値 |
| C5+ | 各USB接続の初回値を除き、Tab5起動後に検出したC5 dropsの増分 |
| DUP | R seqの重複。再同期/リセットとは別 |
| CLIP / G! | 設定・周波数が一致し整定後に検出した、クリップ/ゲイン逸脱のチャネルサンプル数 |

SEQとC5+は同じ欠落を表す場合があるため合算しない。RFの異常理由も重複する。
これらは映像の混信率や電波の占有率ではない。C5のRF診断自体にも更新周期があるため、0だけで完全なRF正常を保証しない。

`rf dump quality` で、上記に加えC5 dropsの絶対値、形式不正、再同期、通信不連続の検出数、
RF取得失敗、代替取得、欠測を読み出せる。`transport_flags` は最後のエラー群を保持し、現在の障害継続を意味しない。
既存 `rf status` / `rf ui` / 各dumpと組み合わせる。新しい操作は読み出しだけで、エラー注入コマンドは追加していない。

## PC・ビルドで確認済み

- Windows/MSVC C++17で、実装と同じdecoder/core/self-testを実行し成功。
  テスト入力は試験用であり、製品のRF表示へ流さない。
- 正常なフレーム→CRC不正→正常なフレームを同じUSB受信塊に入れ、エラー通知順と後続解析を確認。
- seq/dropsの周回・欠番・重複・リセットを確認。
- 正常判定済みの窓へ通信エラーを入れ、灰色化、不完全枠の無効化、有効10秒後の回復を確認。
- 正常基準のOFF/ON記録が通信エラーで失敗し、以前の基準を保持することを確認。
- C5時刻逆行で背景の表示履歴を消す経路でも、不完全枠が正常に戻らないことを確認。
- ESP-IDF 5.4.2、既存lock/依存・buildを使った増分ビルド成功。アプリ1,145,200 bytes、領域余裕25%。
- GitHubにLinux C++17の `tab5-core` jobを追加。ESP-IDF全体のビルド/書込みはこのjobの対象外。

## 実機で確認済み

- ROMでESP32-P4と16MBフラッシュを確認。旧app descriptorは0.5.0。
  USB VID/PIDだけでは書き込み対象を決定していない。接続値は公開しない。
- 更新前にフラッシュ16MB全体をローカルへバックアップ。
- ビルドしたpartition-tableが旧フラッシュと一致すること、アプリの版・領域サイズを照合。
  `0x10000` のアプリだけを書き、esptoolのハッシュ検証成功。bootloader/partition-table/NVSは書いていない。
- 0.5.1起動ログと、実機で全起動時試験 `SELF_TESTS_PASSED` を確認。スタックHWMログは12348 raw。
- 実C5・4ch監視でmask=f、約1923 Rフレーム/秒。起動後の約9〜18千フレーム確認区間で
  CRC・seq欠番・C5 drops増加・重複・形式不正はいずれも0。
- UIの内部ラベルにFILT dB、RAW 100ms履歴、診断レートを確認。描画ログは約4.8ms、最大約9.8msの確認区間。
- 更新後のNVS 24,576 bytesを読み、更新前と全バイト一致。再起動後も保存4ch設定、背景、R8正常基準を読み込み。
  保存済みR8基準のチェックサムは一致。背景・正常基準は自動採用していない。再記録もしていない。

## 未確認と今回の範囲外

物理画面の目視と今回のVTX ON/OFFは、ユーザー確認結果を別途追記するまで未確認。
USB破損フレームの実ケーブルへの注入、長時間連続試験、更新後の本体電源断・再投入は未確認。
通信エラー時の判定はPC/起動時の回帰試験、実C5では通常受信を確認した範囲を区別する。

移動・姿勢変化でも受信は変動する。固定した正常基準の判定を、飛行中の故障/無干渉判定へ一般化しない。
移動観測専用モード、microSD全フレーム保存、独立通過ラベル、AI、自動しきい値は今回追加していない。

## 別PCでの確認・復旧

リポジトリルートの [開発手順](../../../docs/development.md)を参照。
app内の`build.ps1`とESP-IDF 5.4.2を使い、Tab5とC5を取り違えない。
通常ビルドは生成済みフォントCを使うため、Node/fontToolsの準備は不要。

旧0.5.0のソースは更新前のmain commit `adc551e` に保持する。
ローカルの全フラッシュバックアップから旧factoryアプリ領域を取り出した旧appを使う場合も、
書き込み対象を照合し、現在のpartition-tableとの整合を確認した上でアプリだけを戻す。

```sh
# 復旧対象と旧appを照合した後だけ実行
python -m esptool --chip esp32p4 --port <Tab5の確認済みCOM> write_flash 0x10000 <旧app.bin>
```

NVSの全消去・全フラッシュ復元を通常の戻し方にしない。既存設定/基準を保つ。
バックアップ・実測ログ・接続情報はGitへ含めず、個体のローカル資料として保持する。

## 旧文書と実装の食い違い

[正常基準の説明](signal-health.md)は欠測を不採用としていたが、旧 `main/main.cpp` のCRC/seqエラーは
主に `bg_failed` へ渡るだけで、同じ100ms枠に他の有効値があると、正常基準/評価窓へ伝わらない経路があった。
`main/c5_decoder.h` の順序付きエラー通知と `rf_core.h::transport_fault()` で接続し、回帰試験を追加した。
旧版の保存形式や判定の数値条件を変える仕様変更ではない。
